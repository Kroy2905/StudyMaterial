I

AI Fundamentals

the vocabulary everything else is built on

Artificial intelligence, machine learning, and deep learning are often used as if they meant the same thing. They don't — they nest inside one another, each one a narrower way of solving the same broad problem.

Fig. 1 — each field is a narrower approach nested inside the one before it

Inside deep learning, a neural network is just layers of simple math units, each one combining its inputs and passing a signal forward, that together approximate very complicated functions. A CNN is a neural network shaped specifically for images — it slides small filters across a picture to detect edges, textures, and shapes, which is exactly why it matters for your camera work. A transformer is the architecture behind every modern LLM, and you'll meet it properly in the next chapter.

  • Supervised vs. unsupervised — supervised learning trains on labeled examples ("this photo is a cat"); unsupervised learning finds structure with no labels at all.
  • Classification vs. regression — classification picks a category; regression predicts a number.
  • Training vs. inference — training is when the model learns from data; inference is when it's put to work making predictions.
  • Overfitting / underfitting — a model that memorized its training data instead of the pattern, versus one that never learned the pattern well enough.
  • Accuracy, precision, recall, F1 — different lenses for scoring a model — how often it's right, how trustworthy its "yes" is, how many real cases it catches, and a balance of the two.
  • Embeddings — turning text, images, or anything else into a list of numbers where similar meanings end up numerically close together.
  • Tokens & context window — tokens are the chunks text is split into; the context window is how many tokens a model can see at once.
  • Quantization — shrinking a model's numbers to fewer bits so it runs faster and lighter — the difference between a model that fits on a phone and one that doesn't.
in the marginYou don't need to derive backpropagation by hand unless you're aiming specifically at an ML-research role. Know what each term means and when it matters — that's enough to be dangerous.
II

Large Language Models

the single biggest addition to your toolkit

A transformer's defining trick is attention: instead of reading a sentence one word at a time in isolation, it looks at every word against every other word and learns how much each one should influence the rest. That's how a model figures out that "it" refers back to "the phone," three words earlier.

Fig. 2 — self-attention: every token weighing every other token

Everything you do with an LLM is a way of shaping that machinery. A system message sets its behavior and rules for the whole conversation; user messages are the actual back-and-forth. Temperature controls how safe or adventurous its word choices are. Streaming sends tokens back as they're generated, so your UI can display text as it arrives instead of waiting for the whole reply.

Two capabilities turn a chatbot into a real product feature:

  • Structured JSON output — the model replies in a fixed schema your app can parse directly, not a paragraph you have to guess at.
  • Function / tool calling — the model can choose to call a function you've defined, see the result, and keep working — the basis of everything in Chapter IX.
  • RAG — giving the model retrieved facts before it answers, rather than trusting only what it memorized during training. Full chapter ahead.
  • Hallucination — when the model states something false with total confidence — the reason guardrails and evaluation exist.
the shape you're building towardAndroid → backend → LLM → tools/database → response → Android UI. And later, the same shape running entirely on the phone: Android → on-device model → inference → UI.
III

AI APIs

just another backend integration

OpenAI, Gemini, Anthropic, Azure AI, Bedrock, Hugging Face — the providers differ in pricing and personality, but the shape of the integration is nearly identical everywhere. Learn one deeply and the rest come cheap.

Fig. 3 — the lock sits between your app and the provider, not inside the APK

The Android-side chain is: Android → Repository → API client → Backend → AI model → Structured response → Android UI. The one rule that matters more than any provider-specific detail: never put an API key directly inside the APK. Anyone can decompile it and pull the key out — the backend hop exists precisely to keep secrets off the device.

IV

Retrieval-Augmented Generation

give the model something to look up before it answers

An LLM only knows what it learned during training. RAG hands it fresh, specific material at the moment of answering — closer to giving someone an open book than expecting them to recite from memory.

Fig. 4 — documents become searchable meaning, then become an answer

Documents are split into chunks small enough to search precisely. Each chunk becomes an embedding and lands in a vector database. When a question comes in, a similarity search pulls the most relevant chunks and inserts them into the prompt as context — the LLM then answers using material it's actually holding, not just recalling.

the one project to buildAn Android app that answers questions about the user's own PDFs. It's a single project, but it forces you through embeddings, vector search, retrieval, prompting, context management, LLM APIs, streaming, and backend integration all at once.
V

On-Device AI

where your Android background becomes an advantage

Two ladders exist here. The bottom rung is ML Kit — Google's pre-built, no-training-required capabilities: OCR, face detection, barcode scanning, image labeling, pose detection, document scanning. You drop them in and get results.

The rung above is running your own model on the phone with LiteRT / TensorFlow Lite.

Fig. 5 — a model compressed onto a phone, choosing its fastest hardware path

The vocabulary to know: loading a .tflite model, feeding it tensors, the pre- and post-processing that converts a camera frame into what the model expects and its output back into something usable, quantization to shrink it, and choosing between CPU, GPU, and NPU acceleration. Two numbers you'll obsess over: latency and memory. ONNX Runtime Mobile is worth knowing as the other major runtime in this space.

VI

Computer Vision

your camera experience, pointed at models

Every computer-vision feature on Android runs through the same relay: a camera frame comes in, gets prepared for the model, gets interpreted, and the result gets drawn back onto the screen.

Fig. 6 — the same relay, whether it's a bounding box or a skeleton

The vocabulary spans image classification, object detection, segmentation, pose estimation, OCR, tracking, and image embeddings — with OpenCV as the classic toolbox underneath much of it. On Android specifically, this all runs through CameraX's ImageAnalysis pipeline, which is exactly the plumbing your existing camera experience already speaks.

VII

Learning Python

a second language for a different job, not a career change

You're not becoming a Python developer. You're gaining just enough fluency — NumPy for numerical arrays, Pandas for tables of data, Matplotlib for plots, PyTorch for models, Jupyter for quick experiments — to read and adjust the ML code that a data scientist or a paper hands you.

Fig. 7 — two lanes, one destination

Think of Python as the lab and Kotlin as the factory floor. Ideas get tried quickly in Python notebooks; what survives gets exported and shipped through Kotlin. Neither replaces the other.

VIII

PyTorch Basics

the shape of a training run, not a research career

Every training run follows the same loop: examples go in, the model guesses, a loss function scores how wrong the guess was, an optimizer nudges the model's numbers to do better next time, and the cycle repeats until performance on held-out validation data stops improving.

Fig. 8 — the training loop, going round until it's good enough

Once it's good enough, the model takes one more trip: PyTorch model → export/convert → mobile-compatible model → Android → inference. That last step — getting a trained model onto a phone — is worth more to your career than knowing how to train an enormous one from scratch.

IX

AI Agents

a model that acts, not just talks

Give a plain LLM the request "book me a cricket lane tomorrow at 7 PM" and it can only describe what booking a lane might involve. Give it tools — real functions it's allowed to call — and it can actually do it.

Fig. 9 — the model chooses which tool to reach for, then reads the result

The loop is: user → LLM → tool selection → API/database/function → result → LLM → final response. For an Android developer this is the doorway to apps that don't just wrap a chatbot, but genuinely act on the user's behalf.

X

AI App Architecture

the unglamorous skill that actually separates engineers

Knowing fifty AI libraries matters less than knowing how to wire a handful of them into something reliable. In most real products, the backend isn't just talking to one LLM — it's a hub with several spokes.

Fig. 10 — one backend, several specialized spokes

The concerns that live around that hub are what a mature AI product actually needs: security on every API call, streaming, retries and rate limits, caching, watching token cost, latency, observability, keeping prompts under version control, a fallback when a model is unavailable, PII handling, deciding what runs offline versus online, and rolling out model updates without breaking things. None of this shows up in a demo — all of it shows up in production.
