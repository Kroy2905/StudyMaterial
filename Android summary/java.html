Start Here: How Java Code Runs

Q1From .java to running code: JDK vs JRE vs JVM, bytecode, and the JITEasy

Java is compiled and then interpreted/JIT-compiled. javac turns source into platform-independent bytecode (.class files), not machine code. The JVM then loads that bytecode and executes it. That two-step design is what "write once, run anywhere" means: the bytecode is portable, while each OS/CPU gets its own JVM.

// Hello.java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, " + args[0]);
    }
}
$ javac Hello.java      # compile: source → Hello.class (bytecode, NOT machine code)
$ java Hello World      # JVM loads Hello.class, verifies it, calls Hello.main(["World"])
Hello, World
$ javap -c Hello        # disassemble the bytecode the JVM actually runs
  0: getstatic     #7   // Field java/lang/System.out:Ljava/io/PrintStream;
  3: aload_0
  4: iconst_0
  5: aaload             // args[0]
  6: invokedynamic #13  // string concatenation
 11: invokevirtual #17  // Method java/io/PrintStream.println

What the JVM does with a class, step by step:

  • Load: a ClassLoader finds the .class bytes (bootstrap → platform → application loaders, parent-first delegation). Classes load lazily, on first use, not all at startup.
  • Link: verify the bytecode is safe (no stack overflow tricks, type-correct), prepare static fields with default values (0/null/false), resolve symbolic references.
  • Initialize: run static initializers and static {} blocks, once, on first active use (e.g. new, calling a static method, reading a non-constant static field).
  • Execute: the interpreter runs bytecode immediately; methods that get "hot" are compiled to native code by the JIT (C1 quickly, C2 with heavy optimization). That is why Java programs "warm up".

JDK

Development kit = JRE + tools: javac, javap, jar, jdb, jshell. Needed to build.

JRE

Runtime = JVM + the standard class library (java.lang, java.util...). Needed to run. (Since Java 11 it ships inside the JDK / via jlink.)

JVM

The abstract machine: class loader, runtime memory areas (heap, stacks, metaspace), execution engine (interpreter + JIT + GC).

On Android there is no JVM on the device. javac/kotlinc → .class → D8 (or R8 in release builds, which also shrinks and obfuscates) → classes.dex → ART runs dex bytecode using JIT plus profile-guided AOT compilation. Language rules are the same; the runtime is different. See "JVM architecture, and how it relates to ART" further down.
Q2Why is main "public static void main(String[] args)"? What breaks if you change it?Easy
  • public: the launcher calls it from outside your class.
  • static: no object exists yet when the program starts, so the JVM must be able to call it without new App().
  • void: the exit status isn't a return value; use System.exit(code).
  • String[] args: command-line arguments (args.length is 0 when none are given, never null). String... args also works.
public class App {
    public static void main(String[] args) {      // the ONE signature the launcher looks for
        System.out.println("real entry point, args = " + args.length);
        main(42);                                 // you can call the overload yourself
    }

    // Overloading main is legal — but the JVM only ever calls main(String[])
    public static void main(int x) {
        System.out.println("overload called manually with " + x);
    }
}

What the JDK 21 launcher actually says when the signature is wrong:

  • Drop static → Error: Main method is not static in class A
  • Make it private → Error: Main method not found in class B
  • Return int → Error: Main method must return a value of type void
  • Modifier order (static public), parameter name, or String... → works fine.
All of these compile. The check happens at launch time, which makes it a favourite trick question. Since Java 25 (JEP 512), a compact void main() with no public/static/args is also a valid entry point. Interviewers still expect you to explain the classic signature.
Q3Primitive vs reference types: sizes, default values, and where they liveEasy

Integers

byte 8-bit (−128..127) · short 16-bit · int 32-bit (±2.1 billion) · long 64-bit (literal suffix L).

Floating point

float 32-bit (suffix f) · double 64-bit (the default for 1.5). IEEE-754, so they are approximations.

Others

char 16-bit unsigned UTF-16 unit (0..65535) · boolean only true/false, never 0/1.

public class Defaults {
    static int count;          // fields get default values: 0
    static boolean ready;      // false
    static double ratio;       // 0.0
    static char letter;        // '\u0000' (the null character)
    static String name;        // null — every reference type defaults to null

    public static void main(String[] args) {
        int local;
        // System.out.println(local); // compile error: variable local might not have been initialized
        System.out.println(count + " " + ready + " " + ratio + " " + name);

        int b = a;      // copies the VALUE 10
        b++;
        System.out.println(a + " " + b);

        int[] x = {1, 2, 3};
        int[] y = x;    // copies the REFERENCE — both variables point at the same array object
        y[0] = 99;
        System.out.println(x[0]);

  • A primitive variable holds the value itself. A reference variable holds a handle to an object on the heap (or null). Assignment copies whatever the variable holds: the value, or the reference.
  • Local variables live in the method's stack frame and have no default. The compiler enforces "definite assignment".
  • Fields and array elements live on the heap inside their object and get zero-values: 0, 0.0, false, '\u0000', null.
  • Every primitive has a wrapper (Integer, Double...) so it can go into collections and generics. That is autoboxing, covered later.
Q4Is Java pass-by-value or pass-by-reference?Easy

Always pass-by-value. For objects, the value that gets copied is the reference. The method can therefore follow its copy to mutate the same object, but re-pointing the parameter only changes the method's local copy, never the caller's variable.

public class PassByValue {
    static class Box { int value; Box(int v) { value = v; } }

    static void change(int n)      { n = 100; }                 // modifies a local copy
    static void mutate(Box b)      { b.value = 100; }           // follows the copied reference → same object
    static void reassign(Box b)    { b = new Box(500); }        // re-points the LOCAL copy only
    static void swap(Box a, Box b) { Box t = a; a = b; b = t; } // swaps the local copies only

    public static void main(String[] args) {
        int n = 1;
        change(n);
        System.out.println(n);

        Box box = new Box(1);
        mutate(box);
        System.out.println(box.value);

        reassign(box);
        System.out.println(box.value);

        Box p = new Box(1), q = new Box(2);
        swap(p, q);
        System.out.println(p.value + " " + q.value);
    }
}

Q5Variable scope, shadowing, final references, var, and "effectively final"Easy 
import java.util.ArrayList;
import java.util.List;

  • Scope = the enclosing { } block. A variable declared inside a loop or if does not exist after it.
  • Shadowing: a parameter or local with the same name as a field hides the field; use this.value. Java does not let a local shadow another local in an enclosing scope (int x; { int x; } is a compile error).

public class Casting {

        long l = i;                 // widening: implicit, never loses magnitude

Q8Operators: i++ vs ++i, the "j = j++" trap, short-circuiting, and bit shiftsMedium 
public class Operators {
    static boolean check(String name, boolean result) {
        System.out.println("evaluated " + name);
        return result;
    }

    public static void main(String[] args) {
        int i = 5;
        int a = i++;   // post-increment: use the OLD value, then increment
        int b = ++i;   // pre-increment: increment, then use the NEW value
        System.out.println(a + " " + b + " " + i);

        int j = 5;
        j = j++;       // classic trap: j++ yields 5, then the assignment overwrites j with 5
        System.out.println(j);

        int k = 1;
        k = k++ + ++k; // left to right: 1 (k becomes 2) + 3 (k becomes 3) → 4
        System.out.println(k);

        if (check("A", false) && check("B", true)) { }  // && short-circuits: B never runs
        if (check("C", false) &  check("D", true)) { }  // & on booleans evaluates BOTH sides

        System.out.println(-16 >> 2);    // arithmetic shift: keeps the sign bit
        System.out.println(-16 >>> 28);  // logical shift: fills with zeros
        System.out.println((5 & 3) + " " + (5 | 3) + " " + (5 ^ 3)); // 101 vs 011: AND, OR, XOR
        System.out.println(true ? 1 : 2.0); // ternary promotes both branches to one type
    }
}

OOP Fundamentals

Q12Explain the four pillars of OOP — encapsulation, inheritance, polymorphism, abstractionEasy

Encapsulation hides internal state behind methods so invariants can't be violated from outside. Inheritance lets a class reuse and extend another's fields/behavior. Abstraction exposes "what" an object does while hiding "how". Polymorphism lets the same call site behave differently depending on the actual runtime type.

// Encapsulation: hide internal state behind methods
public class BankAccount {
    private double balance; // private = encapsulated

    public void deposit(double amount) {
        if (amount > 0) balance += amount; // controlled access
    }

    public double getBalance() { return balance; }
}

// Inheritance: SavingsAccount reuses BankAccount's state/behavior
public class SavingsAccount extends BankAccount {
    private double interestRate;

    public void applyInterest() {
        deposit(getBalance() * interestRate); // reuse via superclass
    }
}

// Abstraction: expose "what", hide "how" via an abstract class
public abstract class Shape {
    abstract double area(); // no implementation here
}

// Polymorphism: same call, different behavior at runtime
public class Circle extends Shape {
    double radius = 2.0;
    @Override
    double area() { return Math.PI * radius * radius; }
}

Shape s = new Circle(); // reference type Shape, object type Circle
s.area(); // JVM dispatches to Circle.area() at runtime

interface Vehicle {

Q14Method overloading vs overriding — compile-time vs runtime polymorphismEasy 
class Calculator {
    // Overloading: same name, different parameter list — resolved at COMPILE time
    int add(int a, int b) { return a + b; }
    double add(double a, double b) { return a + b; }
    int add(int a, int b, int c) { return a + b + c; }
}

class Animal {
    void sound() { System.out.println("Some sound"); }
}

class Dog extends Animal {
    @Override
    void sound() { System.out.println("Bark"); } // Overriding: resolved at RUNTIME
}

Animal a = new Dog();
a.sound(); // prints "Bark" — dynamic dispatch via the method table (vtable)

Overload resolution is decided purely from the declared argument types at compile time; overriding is decided from the object's actual runtime type via dynamic (virtual) dispatch. Overriding also requires the same signature and a covariant (or same) return type, and can't reduce visibility or add new checked exceptions.

Q16Static vs instance members — memory, access, and initialization orderEasy 
class Counter {
    static int totalCount = 0;   // ONE copy shared by all instances, lives in the Metaspace
    int instanceId;               // a separate copy per object, lives on the heap with it

    static {
        System.out.println("static block — runs ONCE, at class-load time");
    }

    {
        System.out.println("instance block — runs EVERY time, before the constructor body");
    }

    Counter() {
        totalCount++;             // shared state — visible to every instance
        instanceId = totalCount;  // per-object state
    }

    static void printTotal() { // static method: no 'this', can't touch instance members directly
        System.out.println(totalCount);

Q34HashMap internals — buckets, hashing, resize, and Java 8+ treeificationHard 
// Simplified internal structure
class HashMap<K,V> {
    Node<K,V>[] table; // array of buckets, default capacity 16

    static class Node<K,V> {
        final int hash;
        final K key;
        V value;
        Node<K,V> next; // linked list for collisions within one bucket
    }
}

// put(key, value):
// 1. hash = key.hashCode() ^ (hash >>> 16)     -- spreads high bits into low bits
// 2. bucketIndex = hash & (table.length - 1)    -- fast modulo since capacity is a power of 2
// 3. bucket empty -> insert a new Node
// 4. collision -> walk the bucket's list/tree, replace value if a key.equals() match is found,
//    otherwise append
  • Load factor (default 0.75): once size > capacity * loadFactor, the table resizes — capacity doubles and every entry is rehashed into the new table.
  • Treeification (Java 8+): if a single bucket's linked list grows to 8 nodes and the table capacity is at least 64, that bucket converts to a red-black tree — worst-case lookup becomes O(log n) instead of O(n). It untreeifies back to a list if the bucket shrinks to 6 nodes.
Complexity summary: average-case get/put is O(1). Worst case (many collisions) is O(n) pre-Java-8 and O(log n) from Java 8 onward, thanks to treeification.
Q35HashMap vs Hashtable vs ConcurrentHashMap vs LinkedHashMap vs TreeMapMedium
  • HashMap: not synchronized, allows one null key and multiple null values, no ordering guarantee, best general-purpose performance.

    private volatile boolean running = true; // guarantees VISIBILITY across threads

    public void stop() { running = false; }   // the write is immediately visible to other threads

    public void run() {
        while (running) {                     // without volatile, a thread might cache 'running' in a
            // do work                         // register/CPU cache and loop forever, never seeing the write
        }
    }
}

// volatile does NOT guarantee atomicity for compound actions:
private volatile int counter = 0;
counter++; // NOT atomic! read-modify-write is 3 separate steps — still needs
           // synchronized or an Atomic class (Q50) even though it's volatile

The Java Memory Model (JMM) defines when writes by one thread are guaranteed to become visible to another. Without synchronization, the compiler, CPU, and cache hierarchy are all free to reorder or locally cache reads/writes for performance — perfectly legal for single-threaded correctness, but dangerous across threads. volatile establishes a happens-before relationship: every write to a volatile field happens-before every subsequent read of it, and the JVM disables reordering around it. The same happens-before guarantee is also established by entering/exiting a synchronized block and by Thread.start()/Thread.join().

Rule of thumb: use volatile for a simple flag or a "publish this reference once" pattern. The moment you need to read-then-write based on the current value, you need real mutual exclusion (synchronized or an Atomic* class), because visibility alone doesn't prevent a race between two threads' read-modify-write sequences.
Q45wait()/notify()/notifyAll() vs modern concurrency utilitiesHard 
class SharedBuffer {
    private final Object lock = new Object();
    private int data;
    private boolean available = false;

    void produce(int value) {
        synchronized (lock) {
            while (available) {          // ALWAYS a while loop, never 'if' — guards against spurious wakeups
                try { lock.wait(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            }
            data = value;
            available = true;
            lock.notifyAll();            // wake ALL waiters — plain notify() risks missed/starved signals
        }
    }
}

// Modern alternative — prefer this in real code:
BlockingQueue<Integer> queue = new LinkedBlockingQueue<>();
queue.put(value);   // blocks internally if full — no manual wait/notify needed
queue.take();        // blocks internally if empty

wait()/notify()/notifyAll() must be called from inside a synchronized block on that exact object, or the JVM throws IllegalMonitorStateException. They're low-level and easy to misuse; java.util.concurrent (BlockingQueue, CountDownLatch, Semaphore, CompletableFuture, locks/conditions) provides the same coordination with far fewer footguns and should be the default choice today.

Q46Deadlock — causes, a code example, and preventionHard 
Object lockA = new Object();
Object lockB = new Object();

Thread t1 = new Thread(() -> {
    synchronized (lockA) {
        sleep(100);
        synchronized (lockB) { /* ... */ }   // t1 waits for lockB, held by t2
    }
});

Thread t2 = new Thread(() -> {
    synchronized (lockB) {
        sleep(100);
        synchronized (lockA) { /* ... */ }   // t2 waits for lockA, held by t1 -> DEADLOCK
    }
});

Deadlock requires all four Coffman conditions at once: mutual exclusion (locks aren't shareable), hold-and-wait (a thread holds one lock while waiting for another), no preemption (a lock can't be forcibly taken away), and circular wait (a cycle of threads each waiting on the next).

Prevention: always acquire multiple locks in the same fixed global order across all threads (breaks circular wait); use tryLock(timeout) from java.util.concurrent.locks to back off instead of blocking forever; keep critical sections small and avoid nested locks where possible; prefer higher-level, deadlock-resistant utilities (concurrent collections, executors) over hand-rolled locking.

Q50Atomic classes (AtomicInteger) vs synchronizedMedium 
private AtomicInteger counter = new AtomicInteger(0);

void increment() {
    counter.incrementAndGet();      // lock-free — uses CAS (compare-and-swap) at the hardware level
}

// vs the synchronized version — an OS-level monitor lock, heavier under contention
private int syncCounter = 0;
synchronized void incrementSync() { syncCounter++; }

// CAS loop, conceptually:
int prev, next;
do {
    prev = counter.get();
    next = prev + 1;
} while (!counter.compareAndSet(prev, next)); // retry if another thread won the race

Atomic classes are typically faster under low-to-moderate contention because they never block a thread or trigger an OS context switch — a losing thread just retries the CAS. synchronized is simpler to reason about when multiple related fields must change together as one atomic unit, since a CAS only protects a single variable.

Q54Stream API basics — pipeline, laziness, intermediate vs terminal operationsMedium 
List<String> names = List.of("Alice", "Bob", "Charlie", "Dave");

    .filter(n -> n.length() > 3)   // intermediate — LAZY, does nothing yet
    .map(String::toUpperCase)      // intermediate — LAZY
    .sorted()                       // intermediate — LAZY
    .collect(Collectors.toList()); // TERMINAL — triggers the whole pipeline to actually run, once

Intermediate operations (filter, map, sorted, peek) are lazy — they just build up a pipeline description and return a new Stream. Q56JVM architecture, and how it relates to ART on AndroidHard
  • Class Loader Subsystem: loads .class files via Bootstrap → Extension/Platform → Application class loaders (delegation model), then links (verify, prepare, resolve) and initializes each class.
  • Runtime Data Areas: the Method Area/Metaspace (class metadata, static fields), the Heap (all objects, shared across threads), per-thread Stacks (frames of local variables/call state), PC registers, and native method stacks.
  • Execution Engine: an interpreter runs bytecode directly; the JIT (Just-In-Time) compiler profiles hot methods and compiles them to native machine code for speed; the garbage collector reclaims unreachable heap objects.

Relation to ART: Android apps don't run on a standard JVM at all. Source compiles to .class files, which are then converted to DEX bytecode — a register-based instruction set (vs the JVM's stack-based one), optimized for a constrained mobile environment. ART (Android Runtime, which replaced Dalvik starting with Android 5.0) executes that DEX code using a hybrid of AOT (ahead-of-time) compilation at install/idle time and JIT profiling at runtime (since Android 7/Nougat) to balance install time, storage, and steady-state performance. The Java language semantics, garbage collection concepts, and memory model you're tested on all still apply — only the bytecode format and runtime differ.

Q57Stack vs heap memoryMedium 
void method() {
    int localVar = 5;               // primitive -> lives on the STACK frame for this call
    Person p = new Person("Alice"); // 'p' (the reference) is on the stack;
                                     // the actual Person OBJECT is on the HEAP
} // when method() returns, its whole stack frame is popped instantly — localVar and 'p' vanish;
  // the Person object on the heap survives until the GC decides nothing references it anymore

Stack

Per-thread, LIFO. Stores local variables, references, and call frames. Extremely fast to allocate/deallocate (just move a pointer). Fixed size per thread — exceeding it throws StackOverflowError (classic cause: unbounded recursion).

Heap

Shared across all threads. Stores every object and array. Managed by the garbage collector, larger and slower to allocate than the stack. Exhausting it throws OutOfMemoryError.

Q58Garbage collection basics — generational GC and common algorithmsHard

GC is built on the generational hypothesis: most objects die young, so it's cheaper to collect young objects frequently and cheaply, and old objects rarely.

  • Young Generation (Eden + two Survivor spaces, S0/S1): new objects are allocated in Eden. A Minor GC runs often, is fast, and uses a copying algorithm — live objects are copied between Eden/Survivor spaces; objects that survive enough cycles get promoted to the Old Generation.
  • Old Generation: holds long-lived objects. A Major/Full GC runs far less often but is much more expensive since it scans a much larger heap region.

Common collectors: Serial (single-threaded, small heaps); Parallel (multi-threaded, throughput-focused, tolerates longer pauses); CMS (Concurrent Mark-Sweep — low pause but deprecated/removed, suffered from fragmentation); G1 (Garbage First — the default since Java 9, splits the heap into regions and prioritizes collecting the regions with the most garbage first, aiming for predictable pause-time targets); ZGC/Shenandoah (very low, near-constant pause times, designed to scale to huge multi-GB heaps concurrently with the application).
